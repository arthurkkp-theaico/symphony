      How workspaces are actually created

      The orchestrator dispatches an issue to AgentRunner. Before any Codex turn starts, AgentRunner calls Workspace.create_for_issue, then runs workspace hooks, then starts the Codex app-server session inside that directory.

      1
      AgentRunner asks

      Workspace.create_for_issue(issue, worker_host) is the gate before Codex can start.

      2
      Identifier sanitized

      The issue identifier becomes a filesystem-safe id by replacing unsafe characters with _.

      3
      Path resolved

      Local workspaces join workspace.root with the safe id, then canonicalize and validate under root.

      4
      Directory ensured

      Existing directories are reused. Existing non-directories are removed. Missing paths are created.

      5
      Hooks prepare repo

      after_create runs only for new directories. before_run runs before Codex.

      6
      Codex cwd set

      The app-server launches with the workspace as cwd, then thread and turn start with that path.

      Case Behavior Why it matters
      Local workspace workspace.root / safe_issue_id is canonicalized, validated, then created or reused. Keeps Codex execution in deterministic per-issue directories under the configured root.
      Remote worker The daemon sends an SSH script that performs the same directory check and returns the real path. Lets the same orchestration logic target a remote worker host while preserving the workspace contract.
      Fresh workspace after_create may clone, checkout, install deps, or otherwise prepare the repo. Expensive setup runs once per created workspace instead of every continuation turn.
      Every run attempt before_run runs before Codex; after_run runs from an after block. Setup and cleanup are tied to the actual worker attempt, including failure paths.

      Boundary rules

      WORKFLOW.md, issue trackers, workspaces, SSH hosts, and the spawned codex app-server process are outside the daemon. The daemon contains the Elixir modules that read policy, schedule work, create directories, launch Codex, and publish state.

      Inside daemon WorkflowStore, Config, Orchestrator, Workspace, AgentRunner, Codex.AppServer client module, tools, dashboard/API.
      Outside daemon WORKFLOW.md, Linear/Jira, workspace filesystem, remote worker host, spawned Codex app-server process.
      Why Elixir

      It matches the operational shape

      Many concurrent issue workers, supervised subprocesses, retries, timers, PubSub, and LiveView fit BEAM/OTP well.

      Codex role

      Execution, not scheduling

      Codex performs repo reasoning, edits, commands, tests, and tracker tool calls after Symphony creates the run context.

      Portability

      The daemon can be ported

      Go, Rust, TypeScript, Python, or Kotlin can work if they preserve workspace isolation, app-server protocol, retries, and observability.

      Long-horizon agent loop

      How Codex is kept moving across long tasks

      Symphony does not rely on one giant turn. It starts a Codex app-server session in the workspace through Codex.AppServer, sends the full issue prompt from PromptBuilder for turn 1, then starts continuation turns through AgentRunner on the same live thread while the tracker issue is still active.

      Policy file

      WORKFLOW.md

      Human-authored prompt and runtime contract.
      max_turns: 20 Resume from the current workspace state. Do not end while issue remains active. Use exactly one persistent ## Codex Workpad.
      Contributes the horizon budget, durable memory, stop rules, and completion bar.
      Prompt builder

      prompt_builder.ex

      Converts workflow policy plus issue data into the turn-1 prompt.
      Workflow.current() |> prompt_template! Solid.render!(%{ "issue" => issue }) @render_opts strict_variables
      Makes the prompt deterministic: every run starts from current tracker context.
      Codex protocol

      app_server.ex

      Starts the Codex thread and each turn with workspace context.
      "method" => "thread/start" "cwd" => workspace "threadId" => thread_id "text" => prompt
      Keeps every turn tied to the same thread identity and filesystem context.
      Turn loop

      agent_runner.ex

      Runs multiple Codex turns inside one app-server session.
      max_turns = Config.settings!().agent.max_turns turn_number < max_turns -> continue turn_number + 1 Continuation guidance: do not end
      Creates the bounded loop: continue while the issue is active, stop at the cap.
      Scheduler recovery

      orchestrator.ex

      Re-checks active work after a worker exits.
      Agent task completed; scheduling active-state continuation check schedule_issue_retry(... delay_type: :continuation) agent exited; scheduling retry
      Prevents a normal worker exit from being mistaken for permanent completion.
